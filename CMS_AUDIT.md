# Areca CMS implementation audit

## Executive summary

**Overall readiness: a substantial agency CMS implementation, suitable for further controlled evaluation, but with high-risk correctness, isolation, and recovery gaps to resolve before relying on it for production content operations.** Its architecture fits its stated product: schema-driven authoring, owner-controlled releases, immutable content snapshots, and build-time delivery to agency-managed websites. A general runtime query API, GraphQL, a visual builder, complex approval chains, and content localization are not prerequisites for this product.

The implemented strengths are real: PostgreSQL-backed collections and revisions; twelve field types; server-side validation and organization roles; signed draft previews; bounded editor lists; persisted publication/build jobs; Dokploy timeouts and publication-aware health checks; rollback eligibility; upload limits; encrypted deployment credentials; and security headers. These are wired into routes and UI, rather than inferred from dependencies.

The highest-risk confirmed gaps are listed below. In particular, separate `draftData` and `publishedData` do not completely isolate draft changes: the entry slug is shared. Scheduling publishes the current mutable draft, and job completion promotes due entries without checking which entries or versions were actually in that job's snapshot. Asset lookup also lacks tenant scoping in content conversion. Backup/restore and complete authoring exports are absent from the inspected project.

**Validation performed:** 94 tests passed across 15 explicitly selected non-mutating test files. Anonymous GET requests to `/api/sites/manifest`, `/api/sites/snapshot/current`, and `/api/sites/preview` returned HTTP 401 with JSON errors and security headers. `/api/health` returned HTTP 200; `/login` returned HTTP 500. A read-only connection to the locally configured database failed with `ECONNREFUSED`. Browser navigation/snapshot attempts encountered preview automation errors and an empty `chrome-error://chromewebdata/` page. Authenticated editor behavior, installed database migrations, live storage configuration, and real deployment behavior are therefore **Unable to verify at runtime**, not assumed to pass.

## Scope and method

- Audited on 2026-10-01, at commit `2491fb20bd4cb4ef1c1734c46cb3d488a7a9e564`; working tree was clean before the report.
- Inspected `apps/cms` implementation, SQL migrations, configuration, routes, UI components/hooks, unit/integration tests and Playwright specs; also inspected `packages/site-sdk`, the demo-site integration, Docker configuration, image workflows, and relevant root/docs documentation.
- Read-only implementation audit: no source, configuration, schema, credentials, or application data were changed. This report is the sole intentional project-file addition. Database/storage integration tests and E2E suites were not executed: they write data, and `e2e/setup.spec.ts` explicitly resets the database and upload bucket.
- Ran the root Intent skill inventory and loaded the local `@tanstack/react-start#react-start` guidance to assess server boundaries. Library capabilities alone did not count as support.
- In the detailed tables, **paths beginning `src/`, `e2e/`, `scripts/`, or `drizzle/` are relative to `apps/cms/`**. Other paths are relative to the project root. Function names identify the evidence location within a file.
- **Pass** means the inspected implementation meets the scoped capability; it does not imply production runtime certification. **Partial** means usable support with a material gap. **Fail** means existing behavior violates the capability. **Not implemented** means no wired feature was found. **Not applicable** is reserved for documented scope exclusions. **Unable to verify** distinguishes missing operational evidence from demonstrated defects.
- Risks are assessed against the documented agency/build-time use case, not an assumed global SaaS scale. High = plausible content loss, unauthorized exposure, incorrect live state, or difficult recovery. Medium = material reliability/maintenance/usability limitation. Low = conditional feature or limited impact. No Critical exploit or outage was established by this read-only audit.

## Highest-risk confirmed findings

| Priority | Finding and evidence | Failure case / consequence | Recommended next step |
| --- | --- | --- | --- |
| 1 — High | **Tenant checks are missing in content asset/reference conversion.** `src/server/content/snapshot.ts`: image validation/conversion calls `resolveAssetValue(id)` without organization context; preview reference fallback queries only `entry.id`. `src/server/assets/index.ts`: `getAsset` and `resolveAssetValue` accept only ID. | Supplying a known asset ID belonging to another organization can resolve its URL and metadata in a preview or release. Supplying another site's known entry ID in a reference can disclose its slug/collection/ID through preview. Normal picker/list permissions do not protect these direct-write paths. IDs must be known; enumeration or end-to-end exploitation was not demonstrated. | Scope every resolver to the authorized organization/site and expected collection; validate ownership on writes and conversion. Add cross-tenant negative tests. |
| 2 — High | **Draft slug edits can enter a release without owner readiness approval.** `src/server/content/entries.ts:updateDraft` changes `entry.slug`; `src/server/content/snapshot.ts:buildSnapshot` uses `row.slug` with older `publishedData`. | An editor changes the slug of a ready/published entry, then another owner or the scheduler releases the site. The release can use the new address with the previous approved content. Existing live snapshot stays unchanged until that release, but the next publication is not an isolated approved version. | Version the slug with draft/ready data and build exclusively from the approved revision. Test editor slug changes followed by an unrelated release. |
| 3 — High | **Scheduled deployment completion is not tied to snapshot membership or revision.** `src/server/publishing/worker.ts:processJob` promotes every scheduled entry on the site with `scheduledAt <= completion time`, setting `publishedData = current draftData`. | An entry becomes due after the snapshot was captured, or is edited during deployment: it can be marked published even though the deployed snapshot omitted it or contains older content. A rollback can also promote unrelated due entries. Scheduler retries may stop because the affected entry is no longer scheduled. | Persist selected entry/revision IDs in each publication and promote only the matching versions actually deployed. Add controlled-clock, edit-during-build, and rollback-with-due-entry tests. |
| 4 — High | **Scheduling authorizes mutable future content; live content continuity is incomplete.** `entries.ts:scheduleEntry` switches status to `scheduled`; `snapshot.ts:buildSnapshot` excludes scheduled entries until due, then uses current `draftData`. | Editors can continue editing a scheduled draft after an owner schedules it; those edits are automatically released without a separate review. Scheduling a previously published entry causes an unrelated pre-due site release to omit its existing approved version. | Define whether scheduling freezes an approved revision. Keep the currently live/ready version eligible until its replacement is due; display the approved scheduled version clearly. |
| 5 — High | **Stale edits silently overwrite; timed-out navigation loses protection.** `entries.ts:updateDraft` updates by ID only. `features/editor/use-entry-editor.ts` has no expected version; its blocker races save against 3 seconds and blocks only `failed`/`blocked`, allowing `timeout`. | Two users can overwrite entire drafts. Navigation proceeds while a save remains unresolved; a later failure can leave unsaved work with no recovery surface. Local state has no durable recovery buffer. | Add optimistic concurrency and a conflict UI. Treat timeout as unsaved work and keep a recoverable local draft; test delayed failure after navigation. |
| 6 — High | **An absent target or health URL can produce an unverified “live” release.** `worker.ts:processJob` explicitly marks live without deployment when `deploymentTarget` is null; health checking is skipped when URL is absent. `server/admin/sites.ts:deploymentTargetSchema` makes health URL optional. | Production UI can claim content is live without any website being updated, or without verifying the intended publication is served. No-target behavior may help a demo, but it is not explicitly restricted to development. | Introduce an explicit preview/demo mode; require a target and publication-aware health check for production publishing. |
| 7 — High | **Asset deletion can break live content/history, and uploads can orphan objects.** `assets/index.ts:assetUsage` searches only entry JSON for the asset database ID. Rich-text `insertImage` in `features/editor/rich-text/rich-text-editor.tsx` stores a storage-key URL, not that ID. Publications and revisions are not checked. | An image used only in rich text, a historical snapshot, or a deleted entry still present on the live site can be deleted. Upload puts the object before inserting its DB row; failed DB insert leaves an object. Organization deletion cascades asset rows without object cleanup. | Track structured asset usage including rich text and retained snapshots; design retention/garbage collection and upload compensation. |
| 8 — High | **Publication queue safety is incomplete across processes and restarts.** `worker.ts:CLAIM_SQL` excludes active sites but locks only the selected job; no per-site lock or unique active-job constraint exists in `db/schema.ts`/migrations. Stale recovery runs only at startup and only for jobs older than 30 minutes. | With multiple queued jobs for a site, concurrent claim statements can observe no active job and lock different rows. Concurrent enqueue can create those rows. A job interrupted under 30 minutes before restart remains active and blocked after aging because there is no recurring recovery. | Serialize enqueue/claim per site at the database boundary, enforce invariants, add leases/fencing and periodic recovery. Test with independent connections/processes. |
| 9 — High | **Collection keys can escape SDK output directories.** `routes/api/sites/manifest.ts` permits any string collection key; `server/fn/content.ts:upsertCollectionFn` requires only nonempty text. `packages/site-sdk/src/pull.ts` writes `join(outDir, `${key}.json`)` without containment checks. | A manifest key such as `../other` can cause a content pull to overwrite JSON outside the intended directory. Schema authors/site-token holders are trusted today, but an ordinary build token can also POST manifests, widening that trust boundary. | Restrict collection/field identifiers, reject traversal/reserved names, and enforce destination containment in the SDK independently. Separate read and schema-write token privileges if needed. |
| 10 — High | **No complete backup/restore or authoring export/import strategy was found.** `docker/compose.yml` has persistent volumes; `docker/README.md` explains persistence, not backup. SDK export is release JSON with asset URLs; there is no authoring import. | Volume loss, failed migration, or migration away from the product can lose drafts, revisions, asset bytes, permissions, and history. Encryption-key loss makes deployment credentials unrecoverable. | Document and exercise a coordinated DB/object/key restore; provide a versioned authoring export if retention/portability requires it. |

These are code-confirmed implementation findings, with consequences inferred from the stated control flow. They were not reproduced by mutating live data. Public asset URLs are a separately confirmed behavior, not proof that the project promises private media: see §6.3.

## Prioritized remediation plan

### Immediate — before trusting production publishing/data recovery

1. **Close trust-boundary gaps:** tenant-scoped asset/reference resolvers, safe collection/field identifiers and SDK path containment. Explicitly decide public-only versus protected draft assets. Verify fixes with direct boundary tests.
2. **Make approved versions complete and immutable:** include slug and all release values; scheduling selects an approved revision; release completion updates only versions actually deployed. Preserve existing published version until scheduled replacement.
3. **Protect editor work:** optimistic revision checking, timeout-aware navigation protection, durable recovery; make entry/revision/audit mutation results atomic or safely reconciled and retries idempotent.
4. **Make “live” truthful:** require production deploy target and publication-aware health check; distinguish explicit demo/no-deploy mode. Compare pending content/removals against the real live snapshot.
5. **Fix queue/recovery invariants:** per-site database serialization/uniqueness, atomic cancel, recurring lease/stale recovery and independent scheduling cadence. Keep deployment outcome separate from telemetry failures.
6. **Establish tested recovery:** PostgreSQL + object + encryption-key backup/restore runbook, retained historical asset policy and deletion safety. Investigate the currently observed login 500 and unavailable local DB before interactive verification.

### Next — reliability, auditability and verification

1. Add schema-version compatibility/preflight and validate restores; correct historical rollback eligibility migration behavior.
2. Introduce payload/richtext depth limits and SDK/DB deadlines; bound/page history and logs; make SDK pull atomic and remove stale collection files.
3. Complete actor/action audit coverage and atomic log append; add dependency readiness, queue-age/schedule-failure alerts and recovery visibility.
4. Make invitations retryable/resendable after SMTP failure; validate upload bytes and compensate orphaned-object creation/deletion.
5. Gate release workflows with the meaningful unit, isolated DB/route and type checks; test migrations using restored data and document safe rollout.
6. Run the direct-role, failure-oriented and accessibility tests above on an isolated environment; define realistic performance targets and benchmark them.

### Later — only where product requirements justify them

1. **MCP/agent support:** this checklist explicitly requests admin and end-user availability, but current product docs exclude AI features. If agent workflows are now required, build the two permissioned tool surfaces after fixing approval/isolation, with separate identity/audit and draft-only end-user writes. Built-in writing generation is unnecessary.
2. Add a full authoring export/import bundle if customer portability/retention demands it; otherwise document operator extraction and the trade-off. Backup/restore cannot be deferred merely because portability is optional.
3. Image variants/CDN, generic files, repeaters/shared cross-site entries, richer metadata and granular reviewer roles should follow measured customer needs, not checklist scoring.
4. Localization/region variants remain outside the intentional present scope. Revisit them only with a model identity, fallback and publication policy agreed first. A runtime GraphQL/query API, visual page builder, plugin marketplace or real-time collaborative editor is not recommended for completeness alone.

## Readiness conclusion

The code supports the core intended CMS workflow, and the selected read-only tests give useful evidence for its validators and integration adapters. Production readiness is not established: the approval/version, tenant-isolation, concurrent-edit, queue-recovery and backup gaps materially affect that workflow. Resolve and test those before expanding the feature surface; complete authenticated/runtime verification separately from this source-based audit.
