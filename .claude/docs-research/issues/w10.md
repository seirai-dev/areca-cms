# Open issues: w10 (self-hosting: capacity, asset retention, upgrades, backup, troubleshooting)

- capacity: Replica stance conflicts. UPGRADES and OPERATIONS describe extra replicas with WORKER_ENABLED=false, while CAPACITY allows one replica only. Page recommends one replica; the team must confirm a single supported statement (evidence: docs/UPGRADES.md, docs/OPERATIONS.md, docs/CAPACITY.md)
- capacity: No setting for the database pool size; the code passes no max, so node-postgres default of 10 applies. Confirm whether a knob is wanted (evidence: apps/cms/src/db/index.ts)
- capacity: Node heap limit is recommended ("comfortably above 1 GB") but no env var or compose setting documents it, and compose does not pass NODE_OPTIONS (evidence: docs/CAPACITY.md, docker/compose.yml)
- asset-retention: DEPLOYMENT says deleting the asset is the only way to stop its URL working, but deleteAsset refuses referenced assets and no route removes publications or revisions, so a file that reached any release cannot be retracted. Page gives the conservative safe path; a product decision is needed (evidence: docs/DEPLOYMENT.md, docs/ASSET_RETENTION.md, apps/cms/src/server/assets/index.ts, apps/cms/src/server/admin/organizations.ts)
- asset-retention: Cleanup script is not in the Docker image, and the Compose file does not publish the S3 API, so there is no tested way to schedule cleanup in the Docker stack (evidence: apps/cms/Dockerfile, docker/compose.yml, apps/cms/scripts/cleanup-assets.mjs)
- upgrades: Migrations 0009, 0013, 0014 and 0015 exist but have no release notes; page lists only 0007, 0008, 0010, 0011, 0012, 0016 (evidence: apps/cms/drizzle)
- upgrades: No procedure for PostgreSQL major version upgrades (dump and restore) is documented (evidence: docs/UPGRADES.md)
- upgrades: HIGH_RISK asks to retry releases interrupted by the migration and to rename invalid legacy identifiers, but no command or UI path is given; the identifier rules are not stated in any in-scope doc (evidence: docs/HIGH_RISK_UPGRADE.md)
- upgrades: Compose defaults CMS_IMAGE to ghcr.io/ekozf/areca-cms:latest, which contradicts the do-not-follow-latest rule; consider changing the default (evidence: docker/compose.yml)
- backup-and-recovery: docker/RECOVERY.md lacks commands for starting the restored CMS on an isolated port, decrypting a saved credential, recovering interrupted build leases, and verifying counts; page describes these generically (evidence: docker/RECOVERY.md)
- backup-and-recovery: Restored-copy override for port collisions and worker settings is not provided; page tells the operator to write one (evidence: docker/RECOVERY.md, docker/compose.yml)
- backup-and-recovery: Whether Redis holds any durable state that must survive a restore is unclear; page says the project does not say (evidence: docker/RECOVERY.md, docs/OPERATIONS.md)
- backup-and-recovery: docker/RECOVERY.md says the bundle includes encrypted credentials "with their encryption key" and that import requires a matching key. Code writes the key into the bundle in plain text (encryptionKey is always set). Page follows code; RECOVERY wording should be corrected (evidence: apps/cms/scripts/authoring-transfer.mjs, docker/RECOVERY.md)
- troubleshooting: Compose passes only listed variables to the CMS; WORKER_ENABLED, WORKER_CONCURRENCY, LOG_LEVEL and RATE_LIMIT_TRUST_PROXY are not listed, so .env values have no effect. Decide whether to add them (evidence: docker/compose.yml)
- troubleshooting: Compose defaults S3_ACCESS_KEY to areca-demo when unset; consider making it required like S3_SECRET_KEY (evidence: docker/compose.yml)
- troubleshooting: Without RATE_LIMIT_TRUST_PROXY, client IP is 'unknown' so all clients share one rate-limit key; confirm this is intended and document it in rate-limits (evidence: apps/cms/src/server/http/rate-limit.ts)
- troubleshooting: Compose binds the CMS to 127.0.0.1 only, while DEPLOYMENT requires the CMS to be reachable from the Dokploy host; the production answer (reverse proxy or binding) is not documented (evidence: docker/compose.yml, docs/DEPLOYMENT.md)
- troubleshooting: Uncertain dispatch says to follow integration recovery, but no recovery steps are given in the in-scope docs (evidence: docs/TROUBLESHOOTING.md, docs/INTEGRATIONS.md)
