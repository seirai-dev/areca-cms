# Issues from writer w08 (self-hosting: overview, quickstart, production, first-run, configuration)

- production: Replica guidance conflicts. docs/UPGRADES.md allows extra replicas with WORKER_ENABLED=false, while docs/CAPACITY.md says one replica and "do not scale horizontally without reviewing" in-memory state. Page recommends a single replica. Needs one supported statement. (evidence: docs/UPGRADES.md, docs/CAPACITY.md, docs/OPERATIONS.md)
- production / configuration: docker/compose.yml does not pass RATE_LIMIT_TRUST_PROXY, WORKER_*, LOG_LEVEL, ADMIN_MFA_REQUIRED, AUTH_EMAIL_PASSWORD_ENABLED, the SSO/social sign-in variables, or the DOKPLOY_* variables. The page documents adding them to a production copy. Maintainers may want the stock file to pass them. (evidence: docker/compose.yml)
- production: With RATE_LIMIT_TRUST_PROXY=true the CMS takes the first X-Forwarded-For entry (apps/cms/src/server/http/rate-limit.ts:45-55). A proxy that appends instead of replacing lets a client spoof its address. The page tells operators to replace the header. Confirm the intended behaviour, or read the last hop. (evidence: apps/cms/src/server/http/rate-limit.ts)
- production / configuration: The SMTP adapter uses secure:false with no credentials (apps/cms/src/adapters/email/index.ts:29-33). The page says the CMS connects without a username or password and recommends a private relay. Whether STARTTLS is negotiated is not documented. (evidence: apps/cms/src/adapters/email/index.ts)
- production: ALLOW_PRIVATE_HEALTH_CHECKS and DOKPLOY_ALLOW_INSECURE_HTTP are not guarded by NODE_ENV in code (apps/cms/src/server/admin/dokploy-credentials.ts:34-41, 233-245), unlike DOKPLOY_DEV_FALLBACK_ENABLED. The docs say "do not set in production" but the server does not refuse them. Consider refusing in production. (evidence: apps/cms/src/server/admin/dokploy-credentials.ts)
- overview: No tested hardware minimum exists (docs/CAPACITY.md gives only the benchmark on a 16 GB M4 and heap guidance). The page suggests 2 vCPU and 4 GB as a planning figure, not a tested minimum. Needs a measured container minimum. (evidence: docs/CAPACITY.md)
- configuration: VITE_APP_TITLE is declared in apps/cms/src/env.ts:115 but no other source file reads it. The page says it has no effect. Confirm and remove or wire it up. (evidence: apps/cms/src/env.ts)
- configuration: SERVER_URL is declared in apps/cms/src/env.ts:12 and listed in apps/cms/.env.example:51, but nothing reads it. The page says leave it unset. (evidence: apps/cms/src/env.ts, apps/cms/.env.example)
- configuration: LOG_LEVEL is read straight from process.env (apps/cms/src/server/log.ts:228), not validated by env.ts. An invalid value silently falls back to info. The page states this. Consider validating it. (evidence: apps/cms/src/server/log.ts)
- configuration / quickstart: docker/.env.example contains an all-zero DOKPLOY_CREDENTIALS_ENCRYPTION_KEY and a BETTER_AUTH_SECRET placeholder (replace-with-openssl-rand-hex-32). Both pass validation, so a copy that is not edited starts. The quickstart tells readers to replace them. Consider rejecting known placeholders at startup. (evidence: docker/.env.example, apps/cms/src/env.ts)
- configuration: apps/cms/.env.example lists DOKPLOY_CREDENTIALS_ENCRYPTION_KEY under "# Optional" although env.ts requires it. It also has DOKPLOY_ALLOW_INSECURE_HTTP=true and ALLOW_PRIVATE_HEALTH_CHECKS=true uncommented, and BETTER_AUTH_SECRET=change-me, which the validator accepts. Fix the example file. (evidence: apps/cms/.env.example, apps/cms/src/env.ts)
- first-run: The generated setup token is printed when the first page checks whether setup is needed (apps/cms/src/server/admin/setup.ts getSetupStatus). The entrypoint warm-up only requests /api/health (apps/cms/scripts/docker-entrypoint.mjs). So the token is not printed at container start. The page says it appears on first check. Confirm this is intended. (evidence: apps/cms/src/server/admin/setup.ts, apps/cms/scripts/docker-entrypoint.mjs)
- production / asset retention: docs/DEPLOYMENT.md says deleting an asset is the only way to stop its URL working, but docs/ASSET_RETENTION.md says assets referenced by publications, revisions, drafts or archives cannot be deleted. The production page links to asset retention without repeating the claim. The asset-retention page needs an explicit answer. (evidence: docs/DEPLOYMENT.md "Media privacy", docs/ASSET_RETENTION.md)
- production / backup: docker/recovery.mjs takes the Compose project name as an argument. The page uses areca-demo from compose.yml's name field. Confirm whether a renamed production project needs anything beyond the argument. (evidence: docker/recovery.mjs, docker/compose.yml)
