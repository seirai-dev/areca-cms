---
title: Pulling content at build time
description: Download the latest published snapshot with areca pull, understand the generated files, and keep the pull safe in your build.
---

Your site builds from a copy of the published content, not from live CMS requests. `areca pull` downloads the current published snapshot into JSON files in your project, and copies every image and file the content uses into your public folder. Your site then reads those files while it builds and while it serves pages, so neither content nor media depend on the CMS being up. See [media](#media).

Run the pull before every build. Because the files are created during the build, they should be ignored by Git. `areca init` adds the default output and media directories to `.gitignore` for you.

## Run the pull

```bash
pnpm exec areca pull
pnpm exec areca pull --out .cache/areca-content
```

The default output directory is `src/generated/content`. Use `--out` to choose another directory. The command reads `ARECA_CMS_URL` and `ARECA_SITE_TOKEN`, and it loads them from `.env.local` and `.env` if they are not already set. When it succeeds, it prints the publication ID, the snapshot hash and the number of entries in each collection:

```text
Pulled publication <publication-id> (<snapshot-hash>): articles=12, authors=4
Media: 31 file(s) in public/areca (5 downloaded)
```

The pull fails if the site has no published content yet. Publish content in the CMS, then run the pull again.

### From code

If you need the pull in your own script, call `pullContent` from `@areca-cms/site-sdk/pull`. It returns the snapshot it wrote. Unlike the CLI, it only copies media when you pass `assets`:

```ts
import { pullContent } from '@areca-cms/site-sdk/pull'
import { resolve } from 'node:path'

const snapshot = await pullContent({
  outDir: 'src/generated/content',
  assets: { dir: resolve('public/areca'), publicPath: '/areca' },
})
console.log(snapshot.publicationId, snapshot.localAssets)
```

## Add the pull to your build

Add the pull to the `prebuild` script, so it runs before every build:

```json title="package.json"
{
  "scripts": {
    "prebuild": "areca pull --out src/generated/content",
    "build": "vite build"
  }
}
```

With this setup, `pnpm build` pulls the latest content first. In CI, set `ARECA_CMS_URL` and `ARECA_SITE_TOKEN` as secrets for the build job. The site token is a read token, so it is the only token a build needs. See [installation](/docs/sdk/installation#keep-tokens-on-the-server).

## Output layout

Each pull writes one JSON file for each collection into a new folder under `.publications`, then points `manifest.json` at it. Media goes to the media folder.

<Files>
  <Folder name="public" defaultOpen>
    <Folder name="areca" defaultOpen>
      <File name="hero-banner-3f2a91c0.jpg" />
    </Folder>
  </Folder>
  <Folder name="src" defaultOpen>
    <Folder name="generated" defaultOpen>
      <Folder name="content" defaultOpen>
        <File name="manifest.json" />
        <Folder name=".publications" defaultOpen>
          <Folder name="publication-Ab12Cd" defaultOpen>
            <File name="articles.json" />
            <File name="authors.json" />
            <File name=".assets.json" />
          </Folder>
        </Folder>
      </Folder>
    </Folder>
  </Folder>
</Files>

Each collection file, such as `articles.json`, is an array of entries. Each entry has the entry's `id`, `slug`, `publishedAt` (an ISO timestamp, or `null`), its `data` and, when the CMS sends it, its `seo` block. Your site reads these entries with [`readContent`](/docs/sdk/reading-content), which follows `manifest.json` to the right folder.

### manifest.json

`manifest.json` describes the snapshot. Read it to find out which publication your build used.

| Field | Description |
| --- | --- |
| `publicationId` | The ID of the publication the snapshot came from. |
| `hash` | A hash of the snapshot contents. The same content gives the same hash. |
| `createdAt` | When the snapshot was created. |
| `collections` | An object that maps each collection key to its number of entries. |
| `generation` | The folder under `.publications` that holds this snapshot. |
| `assets` | `{ publicPath, count }` when media was copied locally. |

The `collections` object is also the list of collections in the snapshot. Use its keys, not the directory listing, to find out which collections are current.

## Media

By default, the pull copies every image and file the content references (image fields, SEO images, images and file links in rich text) into `public/areca`, and rewrites the content to point at the copies. Your site then serves them like any other static file, and visitors never request anything from the CMS.

- **Image fields** get `url: "/areca/hero-banner-3f2a91c0.jpg"`, so `<img src={image.url}>` works unchanged.
- **Rich text** gets the same paths in `json`, `markdown`, `document` and `html`.
- **SEO data** (`og:image`, `twitter:image`, JSON-LD) gets absolute URLs built from the site's production URL in the CMS, for example `https://www.acme.com/areca/hero-banner-3f2a91c0.jpg`, because social networks and search engines need absolute image URLs.

File names are the original file name as a slug plus part of the file's unique ID. A file is downloaded once; later pulls skip files that are already there.

Configure it with `assets` in `areca.config.ts`. `areca init` asks for these values and writes them for you:

```ts title="areca.config.ts"
export default defineSiteContent({
  siteKey: 'acme-site',
  assets: {
    download: true, // false keeps CMS URLs
    dir: 'public/areca', // relative to the project root
    // publicPath: '/areca', // needed only when dir is not under public/
  },
  collections: { /* ... */ },
})
```

A folder under `public/` is served from the matching path: `public/areca` from `/areca`, `public/media/cms` from `/media/cms`. For other folders, for example `static/` in SvelteKit, set `publicPath` to the URL path your framework serves it from. Without an `assets` block, the defaults apply. The `assets` settings stay in your project: `areca manifest push` does not send them, and `areca manifest pull` keeps them.

The folder must be inside the project: absolute paths and paths that go above the project root are refused. Media files are downloaded from `ARECA_CMS_URL`, with no token. Each download goes to a temporary file first, and the media folder only changes once all of them succeed. If a file fails to download, the pull fails, and the previous content and media stay exactly as they were.

## Snapshot pinning

A pull downloads the snapshot that the CMS gives your site at that moment. The CMS chooses which publication that is:

- **While Areca is building or deploying a release**, the snapshot endpoint returns that release's publication to every caller with a valid site token. The build gets the same content as the release, and so does a pull made during the deployment.
- **Otherwise**, it returns the live publication. A pull on your laptop, with no release in progress, gets this one.

To pull an exact publication, pass `--publication <id>` or set `ARECA_SNAPSHOT_ID`. An empty value or `0` selects the live publication.

Areca's own deployment integration sets `ARECA_SNAPSHOT_ID` as a Docker build argument, and it changes on every build. Docker then cannot reuse a cached content pull from an earlier build, even when the code and CMS settings are the same. If you build with Docker, declare the argument before the build step that runs your `prebuild` pull:

```dockerfile title="Dockerfile"
ARG ARECA_SNAPSHOT_ID=
ENV ARECA_SNAPSHOT_ID=$ARECA_SNAPSHOT_ID
RUN --mount=type=secret,id=ARECA_SITE_TOKEN,required=true \
    ARECA_SITE_TOKEN="$(cat /run/secrets/ARECA_SITE_TOKEN)" \
    pnpm build
```

Mount the site token as a BuildKit secret. Do not pass it as a plain `ARG` or `ENV`, because those values are stored in the image.

## Re-pulling

Each pull writes the new snapshot into a fresh folder and then switches `manifest.json` to it in one rename. If a pull fails, `manifest.json` still points at the previous complete snapshot, and its media files are untouched.

The current folder and the two before it are kept, so a server that read an older `manifest.json` keeps working. Older folders are deleted, together with media files that only they used. Files in the media folder that no pull recorded, such as files you added yourself, are never deleted.

## Running commands with env files

`areca run` runs any command with `.env.local` and `.env` loaded first. Use it when your dev server or build tool does not load env files itself:

```bash
pnpm exec areca run -- vite dev --port 3001
```

The command after `--` is joined with spaces and run through the shell. Pass the whole command as one string if it contains quoted arguments, because the shell sees the joined text and not your original quoting:

```bash
pnpm exec areca run -- "node scripts/build.mjs --label 'site build'"
```

`areca run` exits with the exit code of the command it runs.

## Safety

The pull has several built-in checks. You do not need to add them yourself, but they affect what you can do:

- **Collection keys are checked.** A key that breaks the [identifier rules](/docs/sdk/defining-content#identifiers) stops the pull with an `Unsafe collection or field identifier` error.
- **Files must stay in the output directory.** The pull refuses any path that would be written outside the output directory.
- **Symbolic links are refused.** The pull does not write to a file that is a symlink, and it fails with `Content output must not be a symbolic link`. `readContent` refuses symlinked files too.
- **Output directories are created as needed.** The pull creates the output directory if it does not exist.

Keep the output directory inside your project, and do not commit it. Pulled content is build input, and a fresh pull replaces it.

## Troubleshooting

| Message | What to do |
| --- | --- |
| `No publication exists for this site` | Publish content in the CMS, then run the pull again. |
| `Missing ARECA_CMS_URL` or `Missing ARECA_SITE_TOKEN` | Set the variables in the environment, or in `.env.local` in the directory where you run the command. |
| `Failed to reach CMS` | Check that `ARECA_CMS_URL` is correct and that the CMS is running. |
| `401` | The site token is wrong, or it was rotated. Update `ARECA_SITE_TOKEN`. |
| `Failed to download N media file(s)` | The listed files could not be fetched from `ARECA_CMS_URL`. Check that the CMS serves `/api/assets/file/` from that address, then run the pull again. Nothing was changed. |
| `Pulled, but cleaning up older content failed` | The new content is live. Removing an older generation or its media failed, usually because of file permissions. Fix the permissions; the next pull cleans up again. |
| `assets.dir must be a folder inside the project` | Use a path relative to the project root that stays inside it, such as `public/areca`. |
| `Cannot tell which URL serves <dir>` | The media folder is not under `public/`. Set `assets.publicPath` in `areca.config.ts`. |
| `This CMS version does not list media files` | The CMS is older than the SDK. Update the CMS; until then media URLs point at the CMS. |

See [errors and limits](/docs/sdk/errors-and-limits) for the full list.
