---
title: Draft preview
description: Let editors see draft entries on your site with a signed, one-hour preview token, a server-side preview route and noindex headers.
---

Editors can preview a draft on your website before it goes live. When an editor selects **Preview** on an entry, the CMS signs a short-lived token and opens a URL on your production site. Your site exchanges that token for the draft on the server and renders it with the same view it uses for published content. The draft is never built into a snapshot, and the page is marked so search engines do not index it.

This page covers the whole flow and what your site needs to build. For what editors see, read [Preview](/docs/cms/preview).

## How a preview works

<Steps>
<Step>

**The editor opens a preview.** The CMS signs a token for one entry: the site, the collection, the slug and an expiry time. It then builds a URL of the form `<production URL>/__preview/<collection>/<slug>?token=<token>`.

</Step>
<Step>

**Your route receives the request.** The route at `/__preview/$collection/$slug` runs on your server and reads the `token` query parameter.

</Step>
<Step>

**Your server asks the CMS for the draft.** `getPreviewEntry()` calls the CMS preview endpoint with the token. The CMS checks the token's signature and expiry, then returns the entry.

</Step>
<Step>

**You render the draft with noindex headers.** Send the headers from `previewHeaders()` with the response. Show a clear banner so nobody mistakes the page for published content.

</Step>
</Steps>

For entries, two things are fixed by the CMS and cannot be changed on your side. The path must be `/__preview/<collection>/<slug>`, because the CMS builds that URL. The token is valid for one entry only, so changing the slug in the address bar does not reveal another draft. Site content sections use their own page, described in [Site content previews](#site-content-previews).

## The token

| Property | Behaviour |
| --- | --- |
| Signed | The CMS signs the token with a secret held for each site. A token with a changed payload or signature is rejected. |
| Expiry | Valid for one hour from the time the editor opens the preview. |
| Scope | One site, one collection and one entry. |
| Invalid or expired | The CMS responds with `401`. |
| Entry missing | The CMS responds with `404`. |

Each time an editor opens a preview, the CMS signs a new token. Old tokens do not need to be revoked. They stop working after their expiry time.

The preview token is separate from the site token. The [site token](/docs/security/tokens) reads published content and is used by your build. The preview token authorises one draft.

## Environment variables

The preview helpers use the same client as the build. A preview needs one variable on the server that runs your preview route, at request time and not only during the build.

| Variable | Required | Purpose |
| --- | --- | --- |
| `ARECA_CMS_URL` | Yes | The origin of the CMS, for example `https://cms.example.com`. It is also the origin the visual editor frames the page from. |

The preview request doesn't need `ARECA_SITE_TOKEN`. The CMS authorises it with the signed preview token in the URL, so a server that only serves previews can run without the site token. See [the client](/docs/sdk/client) for the full list of options.

## The preview helpers

| Helper | Signature | Returns |
| --- | --- | --- |
| `getPreviewEntry` | `({ token, client? }) => Promise<PreviewResult>` | `{ kind: 'entry', collection, slug, entry }` or `{ kind: 'global', global, entry }` |
| `previewHeaders` | `() => { 'X-Robots-Tag': 'noindex, nofollow', 'Cache-Control': 'no-store' }` | Headers for the response |

`entry` has the same shape as a published entry, so the view you use for published pages works for drafts too. The optional `client` argument exists for tests. Leave it out in your app.

`getPreviewEntry` throws when the CMS returns an error. The message includes the status code and the CMS's error text, for example `Failed to fetch preview (401): Unauthorized`.

## Typed preview

If your site has the generated `areca.gen.ts`, `content.preview(token)` makes the same request, and returns the entry with the camelCase names and types of your site. Its `collection` is the camelCase key.

The draft is checked against the schema before it is returned, with the same rules as a pull. Editors can save a draft with required fields empty, and a reference or image that points at nothing arrives as `null`. So the result also has a `complete` flag:

- `complete: true`: the draft matches the schema. `entry` is an `Entry`, the same type as a published entry, and `issues` is `[]`.
- `complete: false`: the draft is incomplete. `entry` is a `DraftEntry`, where every field is typed as optional. `issues` lists the problems as `<field>: <problem>`, using camelCase field names, such as `title: is required`.

Check `complete` before you treat `entry` as published content:

```ts
import { content } from '../generated/content/areca.gen'

const result = await content.preview(token)
if (!result.complete) {
  // result.issues: ['title: is required', 'editor: is required']
  return <p>This draft is incomplete: {result.issues.join(', ')}</p>
}
switch (result.collection) {
  case 'blogPosts': // result.entry is Entry<'blogPosts'>
    break
  case 'authors': // result.entry is Entry<'authors'>
    break
}
```

An incomplete draft is not an error, so the call does not throw for it. It throws the same errors as `getPreviewEntry`. A draft from a collection that is not in the generated types throws `Preview collection "<key>" is not in the generated schema`. Run `areca pull` to refresh the types. See [reading content](/docs/sdk/reading-content) for the content object.

## Build the preview route

The example uses TanStack Start, like the [demo site](/docs/sdk/example-site). The data fetch runs in a server function, so the token and site token never reach the browser beyond the URL.

```tsx title="src/routes/[__preview]/$collection/$slug.tsx"
import { createFileRoute } from '@tanstack/react-router'
import { createServerFn } from '@tanstack/react-start'
import { setResponseHeader } from '@tanstack/react-start/server'
import { getPreviewEntry, previewHeaders } from '@areca-cms/site-sdk'
import { z } from 'zod'

const loadPreview = createServerFn({ method: 'GET', strict: { output: false } })
  .validator(z.object({ token: z.string().min(1) }))
  .handler(async ({ data }) => {
    const headers = previewHeaders()
    setResponseHeader('X-Robots-Tag', headers['X-Robots-Tag'])
    setResponseHeader('Cache-Control', headers['Cache-Control'])
    try {
      const preview = await getPreviewEntry({ token: data.token })
      return { ok: true as const, preview }
    } catch (error) {
      const message = error instanceof Error ? error.message : 'Failed to fetch preview'
      return { ok: false as const, error: message }
    }
  })

export const Route = createFileRoute('/__preview/$collection/$slug')({
  validateSearch: (search) => z.object({ token: z.string().min(1) }).parse(search),
  loaderDeps: ({ search }) => ({ token: search.token }),
  loader: ({ deps }) => loadPreview({ data: { token: deps.token } }),
  head: () => ({
    meta: [{ name: 'robots', content: 'noindex, nofollow' }],
  }),
  component: PreviewPage,
})

function PreviewPage() {
  const result = Route.useLoaderData()
  if (!result.ok) {
    return <p role="status">Preview unavailable: {result.error}</p>
  }
  const { entry } = result.preview
  return (
    <main>
      <p role="status">Draft preview. This page is not published.</p>
      <h1>{String(entry.data.title ?? entry.slug)}</h1>
      {/* Render the rest of the entry with the same components as published pages. */}
    </main>
  )
}
```

Replace the status text and the body with your own components. The demo site renders a complete draft with the same article view as a published page, with an extra banner. For an incomplete draft it lists the `issues` instead.

Notes on the example:

- `previewHeaders()` sets the `X-Robots-Tag` and `Cache-Control` headers. The SDK does not add a robots meta tag, so the route adds one in `head()`. The demo does the same.
- The server function sets the headers before it calls the CMS, so they are present on error responses as well.
- The `$collection` and `$slug` URL parameters are for the URL only. The entry comes from the token, so the page shows the draft the token was issued for.

### Keep previews out of prerendering

If you prerender your site, exclude the preview path. The demo does this in its Vite config:

```ts
prerender: {
  filter: (page) => !page.path.startsWith('/__preview'),
}
```

A prerendered preview page would be a copy of a draft, written to disk and served to anyone who requests the file.

## Static sites and Cloudflare

The preview route must run code on every request, because each preview link carries a new token. A site deployed as plain static files has nothing to run that code. The preview then works with `pnpm dev` but fails once the site is deployed. This happens with Cloudflare static assets (a `wrangler.jsonc` with `assets` and no `main`), Cloudflare Pages without Functions, Netlify, GitHub Pages and S3.

### What editors and developers see

In the CMS, **Preview** and the visual editor show the website's 404 page, a blank frame or **Preview unavailable**. The browser console of the CMS tab shows lines like these:

| Console line | Meaning |
| --- | --- |
| `GET https://<site>/__preview/<collection>/<slug>?token=…` with status `404` | No file exists for that path. This is the cause. |
| `GET https://<site>/_serverFn/<hash>?payload=…` with status `404` | TanStack Start only. The route's server function has no server to run on. Same cause. |
| `Minified React error #418` | The browser tried to hydrate the 404 page as the preview route. It follows from the 404s. |
| `Cross-Origin Request Blocked` and `None of the "sha512" hashes in the integrity attribute match` for `static.cloudflareinsights.com/beacon.min.js` | Cloudflare Web Analytics, which Cloudflare adds to the page, is blocked inside the CMS frame. It doesn't affect the preview. To silence it, turn off Web Analytics for the site in the Cloudflare dashboard. |
| `[tiptap warn]: prosemirror-model is loaded more than once` | A warning from the CMS editor itself. It doesn't affect the preview. |

It isn't a CORS problem and it isn't a CMS bug. Changing CORS settings or the CMS doesn't help.

### The fix: static pages, plus a Worker for the preview

Keep every public page prerendered, exactly as before. Add a small handler that runs only for the preview paths, and let every other request go to the static files:

| Path | What the handler returns |
| --- | --- |
| `/__preview/*` | A page shell that renders in the browser, sent with `previewHeaders()` and `visualEditingHeaders({ cmsOrigin })`. |
| `GET /api/preview?token=…&locale=…` | The saved draft from `content.preview(token, { locale })`, as JSON, with the CMS origin. |
| `POST /api/preview/live` | The visual editor's unsaved values, rendered with `content.previewFrom(body)`, as JSON. |

The preview page then loads its draft from `/api/preview` in the browser instead of from a server function. The draft can't be fetched from the CMS directly in the browser, because the CMS preview endpoint sends no CORS headers. The request goes through your own handler.

On Cloudflare, the handler is a Worker deployed next to the static assets. `run_worker_first` sends only the preview paths to it:

```jsonc title="wrangler.jsonc"
{
  "name": "my-site",
  "compatibility_date": "2026-11-01",
  // Lets the SDK read ARECA_CMS_URL from process.env
  "compatibility_flags": ["nodejs_compat"],
  "main": "src/worker.ts",
  "assets": {
    "directory": "./dist/client",
    "binding": "ASSETS",
    "not_found_handling": "404-page",
    "run_worker_first": ["/__preview/*", "/api/preview", "/api/preview/*"]
  },
  "vars": {
    // Public: drafts are read from this CMS, and only it may frame the preview
    "ARECA_CMS_URL": "https://cms.example.com"
  }
}
```

```ts title="src/worker.ts"
import { handlePreviewApi, previewPageHeaders, cmsOriginFrom } from './lib/preview/api'

interface Env {
  ASSETS: { fetch: (request: Request | string) => Promise<Response> }
  ARECA_CMS_URL?: string
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    // GET /api/preview and POST /api/preview/live
    const api = await handlePreviewApi(request, env.ARECA_CMS_URL)
    if (api) return api

    const url = new URL(request.url)
    if (url.pathname.startsWith('/__preview/')) {
      // The client-rendered shell, written by the build (see below)
      const shell = await env.ASSETS.fetch(new URL('/__preview/shell', url).toString())
      const headers = new Headers(shell.headers)
      const extra = previewPageHeaders(cmsOriginFrom(env.ARECA_CMS_URL))
      for (const [name, value] of Object.entries(extra)) headers.set(name, value)
      return new Response(shell.body, { status: shell.status, headers })
    }

    return env.ASSETS.fetch(request)
  },
}
```

`handlePreviewApi` is your own module. Write it as a plain function from `Request` to `Response`, so the same code runs in the Worker and in a Vite middleware for `pnpm dev`. `previewPageHeaders` returns the `X-Robots-Tag` and `Cache-Control` headers from `previewHeaders()`, and the `Content-Security-Policy` from `visualEditingHeaders()` when the CMS origin is known. Send the same `X-Robots-Tag` and `Cache-Control` on the JSON responses too.

In TanStack Start, keep `prerender` and add the `spa` option, which writes the client-rendered shell during the build:

```ts title="vite.config.ts"
tanstackStart({
  prerender: {
    enabled: true,
    filter: (page) => !page.path.startsWith('/__preview') && !page.path.startsWith('/api'),
  },
  spa: {
    enabled: true,
    maskPath: '/__preview/shell/shell',
    prerender: { outputPath: '/__preview/shell' },
  },
})
```

Then set `ssr: false` on the preview route, and make its loader fetch `/api/preview?token=…` instead of calling a server function. With the visual editor, `useLivePreview`'s `resolve` POSTs the result to `/api/preview/live`.

Add `wrangler` as a dev dependency. With pnpm 10, allow `workerd` to run its install script, for example with `allowBuilds: { workerd: true }` in `pnpm-workspace.yaml`.

<Callout type="warn" title="Don't move the whole site into the Worker">
With Cloudflare's Vite plugin, prerendering runs inside the Workers runtime, which can't read the content that `areca pull` wrote to disk. Pages that read content then fail to prerender. Keep the normal build and add the Worker beside it.
</Callout>

A Worker has no project files. `content.preview()` and `content.previewFrom()` call the CMS and convert its answer, so they work there. If your preview page also shows data read from the pulled files, such as referenced entries or site content, test it with `wrangler dev` first.

Other hosts follow the same shape: an Astro adapter with `export const prerender = false` on the preview routes, Netlify or Vercel functions, or Cloudflare Pages Functions for the same three paths.

### Deploy the Worker with Go live

Areca's [Cloudflare deployment](/docs/sdk/go-live-builds#cloudflare-builds) starts a Workers Builds build, which runs your build and then the Worker's deploy command. In Cloudflare, open the Worker's **Settings › Builds** and check that the deploy command is plain `npx wrangler deploy`. A command that uploads only the static files deploys the pages without the Worker, and the preview returns 404 again.

`ARECA_CMS_URL` must be available to the Worker at request time. The build variables that `areca pull` uses are not. Put it in `vars` in `wrangler.jsonc`, as above, or set it as a runtime variable on the Worker.

To check a deployed preview, copy a preview link from the CMS and run:

```bash
curl -sI "<preview link>" | grep -i -E "^HTTP|content-security-policy|cache-control"
# Expect 200, frame-ancestors with the CMS origin, and no-store
```

## Site content previews

A token for a site content section works differently. The CMS opens the section's **preview path** on your site, not `/__preview`. For a section with `previewPath: '/about'`, the link is `<production URL>/about?arecaPreview=<token>`. The page at that path reads the token and shows the draft for that section only.

```ts
import { content } from '../generated/content/areca.gen'
import { getPreviewEntry, previewHeaders } from '@areca-cms/site-sdk'

export async function loadAboutPage(token: string | undefined) {
  if (!token) return { about: content.globals.aboutPage, preview: false, incomplete: false }
  // Send previewHeaders() on this response too (see the headers above).
  try {
    const { globals, previewing, complete } = await content.previewGlobals(token)
    if (previewing === 'aboutPage') {
      return { about: globals.aboutPage, preview: true, incomplete: !complete }
    }
  } catch {
    // An expired or mistyped link shows the published page.
  }
  return { about: content.globals.aboutPage, preview: false, incomplete: false }
}
```

`content.previewGlobals()` returns `previewing`, the section the token targets, so the page can check it matches. When `complete` is `false`, the page shows the published section and a note, as in the example above. A section's draft is shown on its preview path only. An entry token on that page is ignored. The rules for noindex, caching and the token in the URL are the same as for entries. See [site content](/docs/sdk/globals#preview) for the full API.

## Live preview in the visual editor

The CMS [visual editor](/docs/cms/visual-editor) can show this preview route beside the fields and update it as editors type. Your site connects to it with two additions: send the `visualEditingHeaders` policy on this route, and render unsaved results with `useLivePreview` (React) or `createVisualBridge`. Send the policy on preview routes only, never on public pages. See [visual editing](/docs/sdk/visual-editing) for the steps.

## Security

<Callout type="warn" title="The token is in the URL">

Anyone who has the preview URL can read that draft until the token expires. Browsers, proxies, CDNs and access logs can record URLs. Do not log the query string, do not send it to analytics, and do not store it.

</Callout>

- **Keep the site token on the server.** Call `getPreviewEntry` only from server code. Never put `ARECA_SITE_TOKEN` in client code, a public environment variable or a page's HTML.
- **Do not cache preview responses.** `previewHeaders()` sends `Cache-Control: no-store`. Keep it on every response from the preview route, including errors.
- **Do not index preview pages.** Send `X-Robots-Tag` and a robots meta tag. Keep the route out of your sitemap.
- **Treat expired tokens as normal.** An editor who waits more than an hour gets an error and must open the preview again.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| The preview shows the site's 404 page once deployed, but works with `pnpm dev` | The site is deployed as static files, so the preview route never runs. See [Static sites and Cloudflare](#static-sites-and-cloudflare). |
| `Missing ARECA_SITE_TOKEN` | An SDK older than 0.6.0, or the route also reads published content through the client. Previews don't need the site token. Upgrade the SDK, or set the token as a runtime variable. |
| `Failed to fetch preview (401)` | The token expired or was altered. Open the preview again from the CMS. |
| `Failed to fetch preview (404)` | The entry does not exist any more, or the slug changed. |
| `Failed to reach CMS at ...` | `ARECA_CMS_URL` is wrong, or the preview server cannot reach the CMS. |
