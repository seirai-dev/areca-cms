When a release goes live, Areca can redeploy the website through a **deployment target**. A target is a Dokploy application or a Cloudflare Pages project or Worker. This page covers the admin side: connecting a client to a provider, and choosing how each of its sites publishes. For the operator's view of targets and health checks, see [deployment targets](/docs/self-hosting/deployment-targets).

You set this up in two places:

1. **The client** has its own connection to Dokploy and to Cloudflare, shared by all of its sites. A client can have neither, one or both. You set them up under **Agency › Clients › [client] › Deployment**.
2. **Each site** chooses a publishing mode, a provider and a project. You set these under **Settings › Deployment** for that site.

Only agency admins can change either place.

![Deployment tab of a site's settings, showing Publishing mode set to Production, the Dokploy provider, the application ID and the health check URL](/screenshots/current-deployment-settings.png)

## Choose a publishing mode

Each site has a **Publishing mode**, set on **Settings › Deployment**.

| Mode | What happens when a release goes live |
| --- | --- |
| **Production** | Areca builds the release, deploys it to the site's target (a Dokploy application or a Cloudflare project), and checks the health check URL. The release counts as live only after the check passes. |
| **Demo** (labelled "Demo — no production deployment") | Areca builds and records the release, but doesn't deploy it. Demo releases are labelled and never count as live in production. |

Use **Demo** for a site that isn't ready to be deployed, or for local work. Use **Production** for the site the public sees.

## Connect the client to Dokploy

<Steps>
<Step>

**Open the client's Deployment tab.** In the **Agency** workspace, open the client and select **Deployment**.

</Step>
<Step>

**Enter the Dokploy URL.** Use the address of your Dokploy dashboard, such as `https://dokploy.example.com`.

</Step>
<Step>

**Enter the API key.** Areca encrypts the key before storing it and never shows it again. To replace a saved key later, enter a new one. Leave the field blank to keep the current key.

</Step>
<Step>

**Select Save and verify.** Areca checks the credentials and lists the applications they can see. The **Connected** status appears when the connection works.

</Step>
</Steps>

### Test the connection

Use **Verify** to test the saved credentials again at any time, for example after you change something in Dokploy. If the test fails, Areca shows the reason next to the form, such as `Couldn't connect` followed by the error from Dokploy. Fix the URL or key, then verify again.

**Remove credentials** deletes the saved connection. Production sites of this client that deploy with Dokploy then fail to deploy until you add the credentials again.

## Connect the client to Cloudflare

The **Cloudflare** card sits under the Dokploy card on the same tab. It needs a user API token and the client's Account ID. The token needs three permissions, and it must belong to a user, not to the account.

<Steps>
<Step>

**Open the Cloudflare card.** Under **Agency › Clients › [client] › Deployment**, find the **Cloudflare** card. Select **How to set this up** for the guide, which lists the steps and has a **Copy permissions** button.

</Step>
<Step>

**Enter the Account ID and the API token.** The Account ID is 32 hexadecimal characters, from the Workers & Pages overview or the dashboard URL. The token is shown by Cloudflare only once.

</Step>
<Step>

**Select Save and verify.** Areca checks the token and the permissions before it stores anything. The card then shows **Connected**, the last four characters of the token, and the results of four checks: **API token**, **Cloudflare Pages**, **Workers Scripts** and **Workers Builds**.

</Step>
</Steps>

If a check fails, Areca still saves the token and reports **Saved, but some checks failed.** Add the missing permission in Cloudflare, then select **Verify**. **Remove** deletes the saved token and Account ID. Sites that deploy with Cloudflare then fail their next go-live until you add the credentials again.

The full token steps, the checks and the encryption key are in [deployment targets](/docs/self-hosting/deployment-targets#cloudflare).

![Cloudflare card on a client's Deployment tab, showing Connected, the Account ID, the masked token and four passed checks: API token, Cloudflare Pages, Workers Scripts and Workers Builds](/screenshots/cloudflare-client-card.png)

## Choose a provider for a site

Open the site's **Settings › Deployment** tab. Under **Provider**, select **Dokploy** or **Cloudflare**. The site is built and hosted by the provider you choose when it goes live.

- A provider that the client has not connected is disabled, with a link such as **Set up Cloudflare for `<client>`** that opens the client's Deployment settings.
- When the client is connected, the row shows **Connected for `<client>`** and **Manage in Agency**.
- Switching the provider clears the chosen target. Choose the project again after you switch.
- You can't save changes while a deployment is pending.

## Set the application for a Dokploy site

With **Dokploy** selected, choose the application for the site.

- **Application.** When the client is connected, Areca lists the Dokploy applications the credentials can see. Select one from the list. If the list is long, search it by name.
- **Or enter the application ID.** If you can't see the application in the list, type its ID. Find it in the application's URL in Dokploy. Areca marks an ID that isn't in the list as **Not in the list**.
- **Health check URL.** The address Areca calls after each deploy. It must use `http` or `https`, and it must report the publication ID that Areca sends to the site. The field is required in Production mode, and Go live is blocked until it is set. Demo sites skip the health check. See [deployment targets](/docs/self-hosting/deployment-targets) for the details.

Select **Save** to store the changes.

Areca checks the health URL after each deploy, not when you save. To confirm the URL works before you go live, open it in a browser and check that it responds.

## Choose a Cloudflare project

With **Cloudflare** selected, choose the project in the **Project** field. This is a single searchable picker, and it has no field for entering an ID by hand.

![The Cloudflare project picker open, with the Pages group showing marketing-site and a disabled legacy-upload project marked No git connection, and the Workers group showing northbound-worker and a disabled plain-worker marked Workers Builds not connected](/screenshots/cloudflare-site-picker.png)

- **Search.** Type to filter the list. The search matches the project name, the domain and the branch.
- **Groups.** Projects are grouped under **Pages** and **Workers**.
- **Rows.** Each row shows the project name, its production branch and its main domain.
- **Disabled rows.** A project that cannot be built is disabled, with the reason beside it. A Pages project without a Git connection shows **No git connection**. A Worker without Workers Builds shows **Workers Builds not connected**.
- **Refresh list.** Select the refresh icon to reload the list from Cloudflare.

When you choose a project, Areca saves its production branch and shows it as **Builds branch**. For a Pages project, this is the project's production branch. For a Worker, it is the branch of the build trigger. To pick up a change in Cloudflare, choose the project again.

For a Worker, Areca chooses the trigger for the production branch automatically. If more than one trigger matches, a **Build trigger** select appears, with the note "The trigger for the production branch. Preview uploads never go live."

**Health check URL** is filled in from the project's first custom domain, followed by `/api/health`. If there is no custom domain, Areca uses `<project>.pages.dev` for a Pages project, or `<worker>.<account-subdomain>.workers.dev` for a Worker. Edit it if the site serves its health route somewhere else. The field is required in Production mode, and Go live is blocked until it is set.

If a saved project no longer exists in Cloudflare, the picker shows **Not found in Cloudflare — choose again**. Choose another project before you go live.

When the site is saved, the status reads **Deploying to Cloudflare Pages project `<name>`** or **Deploying to Cloudflare Worker `<name>`**. **Stop deploying…** works the same way as for Dokploy.

![The Deployment tab of a site set to Cloudflare, with Production mode, the Cloudflare provider marked Connected, the Worker shop-worker chosen as the project, and its Builds branch main](/screenshots/cloudflare-deployment-settings.png)

Select **Save** to store the changes.

## Stop deploying

**Stop deploying…** removes the target and the health check URL from a site. The site stops deploying through its provider. It works for both Dokploy and Cloudflare.

<Callout type="warn" title="A Production site can't go live without a target">
If the site is still in **Production** mode, Go live is blocked until you choose a target and a health check URL again. To release without deploying, switch the site to **Demo** first.
</Callout>
