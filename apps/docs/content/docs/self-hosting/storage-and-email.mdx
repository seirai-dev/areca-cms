Areca needs an S3-compatible bucket for uploaded images and files. It also needs an SMTP server to send email, such as invitations. The bucket is required at startup. The mail server is optional: without one, mail is off until you set one up. This page explains how each one is used, and how to check that it works. For every variable, see [configuration](/docs/self-hosting/configuration).

## S3-compatible storage

Every uploaded asset and branding file is stored in one bucket. The CMS reads and writes the bucket with the access key you provide. Browsers never connect to the bucket directly.

| Variable | What it is |
| --- | --- |
| `S3_ENDPOINT` | The full URL of the storage API, for example `https://s3.eu-central-1.example.com` or `http://rustfs:9000` in the Docker Compose stack. |
| `S3_REGION` | The region name the provider expects. Use the value from your provider's documentation. |
| `S3_BUCKET` | The bucket name. Areca uses this bucket only. |
| `S3_ACCESS_KEY` and `S3_SECRET_KEY` | Credentials with read, write and delete access to the bucket. |
| `S3_FORCE_PATH_STYLE` | Set to `true` for servers that need path-style URLs, such as MinIO and RustFS. The default is `false`. |

### Create the bucket

The bucket must exist before the CMS starts. You have two options:

- **Docker image.** The container entrypoint checks for the bucket on every start and creates it if it is missing. You do not need to do anything extra.
- **Running from source.** Run the bucket script from the repository root, with the storage variables in `apps/cms/.env.local`:

```bash title="Terminal"
pnpm --filter @areca/cms s3:init
```

The script checks for the bucket and creates it if it is missing. It is safe to run more than once.

<Callout type="warn" title="The access key can read every upload">

The S3 key pair has full access to every stored file. Keep it in your secrets store or host environment, not in the repository. Rotate it at the provider and update the CMS environment. Rotating the key does not touch the stored objects.
</Callout>

## Public assets and the CDN

Uploaded files are public. The CMS serves each one at a URL under `/api/assets/file/` without asking for a sign-in. The URL contains a random ID, so anyone who has the link can open the file. Links also appear in page source, referrer headers and shared links.

This applies to assets attached to drafts, unpublished entries and archived content, not only to live pages. Draft text is protected by sign-in and preview tokens, but its images are not. Do not upload embargoed or confidential material.

Keep the S3 bucket private. The CMS is the only thing that should reach it.

To serve assets through a CDN:

- Point the CDN at the CMS origin, not at the bucket.
- Cache only the `/api/assets/file/` path. Do not cache other `/api/` routes or the application's pages, because those depend on sign-in.
- Forward only the path. Ignore cookies and the `Authorization` header on asset requests.
- Respect the `Cache-Control` header from the origin. The CMS sends `public, max-age=31536000, immutable` for assets, because each file name is unique.

Keep `APP_URL` set to the CMS origin, not the CDN, unless your CDN rewrites asset URLs.

Assets stay in storage while any draft, revision, release or archive still refers to them. Read [asset retention](/docs/self-hosting/asset-retention) before you remove files.

## Email (SMTP)

The CMS sends email through an SMTP server. The server's host, port and encryption come from the `SMTP_*` variables, or from **Agency** > **Mail** after you sign in. Settings saved in **Agency** > **Mail** replace the environment settings completely. For the variables, see [configuration](/docs/self-hosting/configuration#email). For the screen, see [agency mail](/docs/cms/agency-mail).

If you set no server in either place, mail is off. Invitations still work, and you can share the link with **Copy link**. Forgot password tells people to ask an agency admin, and security notices are not sent.

The sender's display name comes from the [branding](/docs/cms/branding) settings. The sender address comes from `SMTP_FROM` or from **Agency** > **Mail**.

### What gets sent

- **Invitations** to join a client.
- **Password reset** links, from the sign-in page or from an agency admin.
- **Email verification** links.
- **Security notices**: password changed, two-factor authentication turned on or off, removed from a client, and role changed. These cannot be turned off. See [your account and sign-in](/docs/cms/account-and-sign-in#security-emails).

### How sending works

When you invite someone, resend an invitation, or send a test, the CMS tries to send the email straight away, so you see the result at once.

If the try fails, the email is queued and tried again. Areca retries about 1 minute after the first try, and again about 5 minutes after that. If the last try fails too, the email is marked **failed**. Some errors will not be fixed by waiting, such as a rejected password or a refused recipient. Those fail at once, without retries.

Each connection has a 15-second timeout for connecting, for the server's greeting and for the socket. The CMS always verifies the server's certificate.

A status of **sent** means the mail server accepted the message. It does not confirm that the message reached an inbox.

### Reset links in the queue

A password reset link is a secret, so the queue does not keep it in plain text. When a key is set, Areca stores the reset token encrypted, using `SECRETS_ENCRYPTION_KEY`, or `AI_SETTINGS_ENCRYPTION_KEY` if that is unset. Generate the key with `openssl rand -base64 32`, and keep it with your database backups.

Without either key, Areca stores no token. A reset email is then tried once, straight away, and is not retried if that try fails. The person must ask for a new link.

### Where failures show

- **A toast** appears after you send an invitation, resend one, or send a test, if the send fails.
- **The People list** shows **Email not delivered** on the pending invitation, with the reason in plain language. See [people and invitations](/docs/cms/people-and-invitations).
- **Recent emails** in **Agency** > **Mail** lists the last 50 emails, with the status and error for each failure. Use the filter to show only failed emails.
- **A banner** appears for agency admins after three emails in a row fail. It links to Recent emails.

### Find details in the logs

Each send is logged under the `mail` component. Each entry includes the outbox ID, the kind of email, the attempt number, the host and port, and the mail server's response code. It never includes the SMTP password, the invitation link or other tokens.

To find the log entries for one email, copy its outbox ID from the row in **Recent emails**, or from the message in the UI, and search the logs for it.

### Email providers

Most people send through a transactional email provider. Use the values from your provider's dashboard, because they depend on your account. These are the usual settings:

| Provider | Host | Port | Security | Username | Password |
| --- | --- | --- | --- | --- | --- |
| Resend | `smtp.resend.com` | `465` or `587` | `tls` on 465, `starttls` on 587 | `resend` | Your Resend API key |
| Postmark | `smtp.postmarkapp.com` | `587` | `starttls` | Your server API token | The same server API token |
| Amazon SES | `email-smtp.<region>.amazonaws.com` | `587` | `starttls` | Your SMTP user name | Your SMTP password |
| Mailgun | `smtp.mailgun.org`, or `smtp.eu.mailgun.org` for EU domains | `587` | `starttls` | `postmaster@` your sending domain | Your domain's SMTP password |
| Google Workspace | `smtp.gmail.com` | `587` | `starttls` | Your full Google address | An app password |

Notes for each provider:

- **Resend** uses the API key as the password. Create a key with permission to send.
- **Postmark** uses the same server token for both the username and the password.
- **Amazon SES** needs SMTP credentials, which you create in the SES console. Do not use your IAM access keys. Replace `<region>` with the region where you verified your domain.
- **Mailgun** uses the SMTP credentials of the domain you send from. Use the EU host if the domain was created in the EU region.
- **Google Workspace** needs an app password. Create one in your Google account, which requires 2-step verification to be on.

Set the sender address to an address on a domain you have verified with the provider, such as `cms@agency.example`.

### Deliverability

Email sent from your domain has the best chance of reaching an inbox when the domain proves that the provider may send for it. Set this up once, before you invite clients.

1. **Verify the sending domain** in your provider's dashboard. The provider shows the DNS records to add.
2. **Add the SPF record.** This is a TXT record on the sending domain that lists the servers allowed to send for it. Use the value your provider gives you. A domain should have only one SPF record.
3. **Add the DKIM records.** The provider gives you one or more records. They let receivers check that the message was not changed in transit.
4. **Add a DMARC record** at `_dmarc.<your domain>`, for example:

   ```txt title="DNS TXT record for _dmarc.agency.example"
   v=DMARC1; p=quarantine; rua=mailto:dmarc@agency.example
   ```

   `p=quarantine` tells receivers to treat messages that fail SPF and DKIM as suspicious. Some teams start with `p=none` while they read the reports sent to the `rua` address.
5. **Use a From address on that domain.** Mail from a domain you have not verified can fail these checks, or be refused by the provider. If the provider refuses it, Areca shows the message in [agency mail](/docs/cms/agency-mail#troubleshooting-errors).

The DNS records take effect after they are published, so allow some time before you test. Your provider's dashboard shows when the domain is verified.

## Test delivery

Test email before you invite real clients:

<Steps>
<Step>

**Set up the mail server.** Either set the `SMTP_*` variables for the stack, or sign in and enter the server in **Agency** > **Mail**. For a local stack, the Docker Compose file points the CMS at a Mailpit container on port `1025`. Mailpit's inbox is at `http://localhost:8025`.

</Step>
<Step>

**Restart the CMS if you changed variables.** Environment changes apply only after a restart. Settings saved in **Agency** > **Mail** apply straight away.

</Step>
<Step>

**Send a test email.** In **Agency** > **Mail**, select **Verify connection**, then **Send test email**. The message goes to your own address.

</Step>
<Step>

**Invite a test address.** Use an address you control, and invite it from the People list.

</Step>
<Step>

**Check the inbox.** Open the message, and check that the link opens the invitation page.

</Step>
<Step>

**Check the result if it fails.** Open **Recent emails** in **Agency** > **Mail**. It shows the reason for each failure. The CMS log has the same details under the `mail` component.

</Step>
</Steps>

Also check the storage path. Upload a small image in the CMS, and confirm that it loads from `/api/assets/file/` on your public CMS address.
