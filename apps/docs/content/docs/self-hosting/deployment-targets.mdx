When a site goes live, Areca asks [Dokploy](https://dokploy.com) to build the website and deploy it. Areca does not build the site itself. It pins the content snapshot, starts the Dokploy build, waits for the new container, and checks that it serves the release before marking the release live.

This page is for operators. It covers how to connect Dokploy to your Areca instance and how the deployment works underneath. To assign a deployment to a site and see its status in the admin interface, read [deployments](/docs/cms/deployments).

<Callout>

Dokploy is the only deployment provider. Demo sites do not use it. See [the publishing pipeline](/docs/self-hosting/publishing-pipeline) for the full release flow.

</Callout>

## What you need

- A Dokploy instance that the CMS can reach over HTTPS.
- A Git repository for each website that Dokploy can clone. A private GitHub repository works if Dokploy has a read-only deploy key for it.
- A CMS address that the Dokploy build host can reach. `localhost` in the CMS settings means the build container, not your server, so use the public or private network address of the CMS.
- The website's Dockerfile, which runs `areca pull` during the build. See [go-live builds](/docs/sdk/go-live-builds). Demo sites skip the deploy and the health check, so they need no health URL.

## Connect a Dokploy application

Each client site needs one Dokploy application. You can create it by hand, or use the repository's `dokploy:setup` script, which does the same steps through the Dokploy API. The script is intended for onboarding and local testing.

<Steps>
<Step>

**Create the application.** Add an application in Dokploy that builds from your website repository with the Dockerfile build type.

</Step>
<Step>

**Turn off deploy on push.** Only a Go live request should start a build. Leave automatic deployment off.

</Step>
<Step>

**Publish a host port.** Map a port on the Dokploy host to the port the website listens on, for example `3101` to `3000`. Use host publishing mode.

</Step>
<Step>

**Set the update order to stop-first.** Dokploy's default start-first order cannot bind the same host port twice. Stop-first lets the new container take the port after the old one stops.

</Step>
<Step>

**Save the credentials in Areca.** Open the client under **Agency**, then **Clients**, then the client's **Deployment** section. Enter the Dokploy URL and API key, and select **Save and verify**. Areca lists the applications the key can see.

</Step>
<Step>

**Assign the application to the site.** In the site's **Deployment** settings, choose the application from the list (or enter its ID), enter the health check URL, and set the site to production.

</Step>
</Steps>

Saving or removing Dokploy credentials requires a fresh two-factor code. See [two-factor authentication and step-up](/docs/security/two-factor-and-step-up).

## Credentials and encryption

Each client has its own Dokploy URL and API key. Areca stores the API key encrypted in the database, using AES-256-GCM with the organization as part of the encryption context. After you save a key, the admin interface shows only its status. The key is never displayed again.

The encryption key comes from `DOKPLOY_CREDENTIALS_ENCRYPTION_KEY`. It must be a base64-encoded 32-byte value, and the CMS will not start without it. Generate one with:

```bash title="Terminal"
openssl rand -base64 32
```

<Callout type="warn" title="Back up the key with the database">

There is no re-encryption tool. If you lose `DOKPLOY_CREDENTIALS_ENCRYPTION_KEY`, or change it, every saved Dokploy key becomes unreadable, and each client's key must be entered again. Keep the key with your database backups, and never change it during an upgrade or a restore. The key must also be the same on every CMS instance that shares the database.

</Callout>

To rotate a Dokploy API key, create a new key in Dokploy, save it for the client in Areca, select **Save and verify**, and then revoke the old key in Dokploy.

The legacy process-wide `DOKPLOY_URL` and `DOKPLOY_API_KEY` pair is for local development only. It is used only when `DOKPLOY_DEV_FALLBACK_ENABLED=true` in a non-production environment, and production ignores it.

## How the snapshot reaches the build

Every Go live request creates a publication with an immutable snapshot. Before it asks Dokploy to deploy, Areca writes the publication ID into the application's build arguments:

- `ARECA_SNAPSHOT_ID` is a Docker build argument, set to the publication ID for the release being built.
- `ARECA_CMS_URL` is also a build argument. It is the address the build uses to reach the CMS.
- `ARECA_SITE_TOKEN` is passed as a BuildKit secret, not as a build argument or an image environment variable. The Dockerfile mounts it only for the step that pulls content, so it is not stored in an image layer.

The Dockerfile must declare `ARG ARECA_SNAPSHOT_ID` immediately before the step that runs `areca pull`, after the SDK is built. A Docker build caches each step, and changing the argument invalidates only the layers after it. If the argument is declared too early, Docker reuses the cached content pull from an earlier release, and the new container serves old content. The health check then fails, and the release is not marked live.

Areca also tags each Dokploy deployment with `areca:<jobId>` as its title, and writes the publication ID and snapshot hash into its description. You need these values to find a deployment when you reconcile an uncertain release.

## Health checks

Production sites must set a health check URL. Areca polls it until it returns HTTP 200 with a JSON body whose `publicationId` matches the release being built. A plain 200 response is not enough, because the previous container could still be serving. Your website must return the publication ID from its health route. See [go-live builds](/docs/sdk/go-live-builds). Demo sites skip the deploy and the health check, so they need no health URL.

A typical health check URL for a host-published port is:

```text title="Health check URL"
https://www.client-site.example/api/health
```

Areca follows up to four redirects, and checks the final response. If the check fails within two minutes, the release fails and the previous release stays live.

## HTTPS and private addresses

Areca enforces these rules on every outbound connection to Dokploy and to health check URLs:

- **The Dokploy API must use HTTPS.** Plain HTTP is accepted only for `localhost`, or when `DOKPLOY_ALLOW_INSECURE_HTTP=true`. Redirects are rejected, and the API URL must not contain a user name or password.
- **Health checks must use HTTP or HTTPS.** Areca refuses a health check URL that resolves to a private or reserved address, such as a loopback, link-local or RFC 1918 address. It connects to the address it checked, so a name cannot be changed between the check and the request.
- **Local and LAN testing needs two switches.** To test against a LAN address over HTTP, set `DOKPLOY_ALLOW_INSECURE_HTTP=true` and `ALLOW_PRIVATE_HEALTH_CHECKS=true`.

<Callout type="warn" title="Do not enable these on a public CMS">

`DOKPLOY_ALLOW_INSECURE_HTTP` and `ALLOW_PRIVATE_HEALTH_CHECKS` weaken the protections above. Use them only on an isolated local or LAN instance, never on a CMS that clients or the internet can reach.

</Callout>

For the variables, see [configuration](/docs/self-hosting/configuration).

## Timeouts and retries

| Operation | Limit | On failure |
| --- | --- | --- |
| Dokploy API request | 15 seconds | Counted as a failed attempt. |
| Read calls and identical environment writes | Up to 3 attempts, with a short backoff of about 100 ms and then 200 ms | Retried on network errors and on HTTP 408, 429, 500, 502, 503 and 504. Other HTTP errors are not retried. |
| Deploy request | Sent once, never retried | If the response is lost or ambiguous, Areca searches Dokploy for the tagged deployment for up to 30 seconds. |
| Deployment completion | Checked every 5 seconds, for up to 15 minutes | The release fails if Dokploy reports an error. It becomes uncertain if the wait runs out. |
| Health check | Checked every 5 seconds, for up to 2 minutes | The release fails. |
| Build job lease | 60 seconds, renewed every 15 seconds | See the [publishing pipeline](/docs/self-hosting/publishing-pipeline). |

The deploy request is never retried automatically, because a retry could start a second build. If Areca cannot confirm whether the deploy request was accepted, the release becomes uncertain and waits for you to reconcile it. The [publishing pipeline](/docs/self-hosting/publishing-pipeline#uncertain-deployments) explains how.
