# Areca CMS VPS capacity benchmark

**200 concurrent users passed. 500 concurrent users failed the latency limits.** The failure was sustained slowness, not request errors or a service crash. The tested capacity boundary lies between 200 and 500 users for this workload; this does not establish an exact maximum.

## Formal results

Each tier used a fresh database baseline, app restart, cooldown, 60-second ramp, 60-second settling period and a **600-second measured window**. Percentiles and throughput below exclude ramp/settling/shutdown. All tested tiers also passed the logical-action error check. There were **89,675 measured requests** in total.

### When the failure appeared

The 500-user measured window ran approximately **00:58:18–01:08:18 CET on November 3, 2026** (23:58:18–00:08:18 UTC). Latency was already outside the limits at its beginning, after ramp and settling: the first measured slow sample was `updateAssetFn`, **3,911 ms**. The failure persisted throughout the ten-minute window. The 200-user tier had occasional >1-second outliers but passed its aggregate percentiles.

The throughput increase from 200 to 500 users was modest relative to the increase in concurrency: requests accumulated in queues rather than scaling proportionally.

## Which component limited the run?

**Strongest evidence: the CMS's Node request/database-client path, including its saturated connection pool and excessive per-request work. PostgreSQL itself was not saturated in the same way.**

| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CMS        | Average container CPU **111.9% of one core**, peak 154.0%; broad RPC latency in seconds. ## Diagnostic evidence, excluded from formal acceptance

Two short 500-user replays were kept separate from the six formal tiers. The first captured a CPU trace; the second verified the pool/event-loop probe after correcting an inspector compatibility issue. The verified 30-second capture showed:

- Pool: **10 total, 0 idle**, 213–271 waiting operations.
- Event loop: essentially **100% utilized** over the capture interval.
- About **23% of sampled main-thread time** in the bundled Drizzle/PostgreSQL client code; a PostgreSQL socket-write stack alone accounted for about **9%**; garbage collection about **7.4%**. Authentication/context creation and serialization were also visible hotspots.
- The formal 500-user interval recorded **447,276 database commits for 37,611 HTTP requests**, roughly 12 transactions/request including background activity. This is evidence of a chatty request path, not a precise per-endpoint SQL count.

CPU profiling used the [Node inspector profiler](https://nodejs.org/docs/latest-v24.x/api/inspector.html), enabled only on container loopback and closed afterward. The application and deployed configuration were not changed to improve results during the formal run.

### Storage-path microcheck

A separate sequential check used 444,910-byte objects, **12 samples per operation/configuration**, and deleted its test objects. It ran after load traffic stopped, bypassed image validation and the CMS database, and is not a concurrency test.

| Configuration                          | Median PUT, ms | Median GET, ms | Median DELETE, ms |
| -------------------------------------- | -------------: | -------------: | ----------------: |
| Fresh S3 client, public HTTPS endpoint |           80.3 |           61.7 |              89.0 |
| Reused client, public HTTPS endpoint   |           24.6 |           13.8 |              43.5 |
| Fresh client, internal endpoint        |           22.1 |           11.2 |              44.3 |
| Reused client, internal endpoint       |           25.8 |            7.1 |              35.9 |

All microcheck operations succeeded. A second check reproduced the same direction: median GET was 65.1 ms with fresh/public versus 6.6 ms with reused/internal. These small sequential, ordered checks support testing client reuse/internal routing, but do not establish how much concurrent CMS capacity that change would add. Cache/order effects remain possible. They do not explain away the general RPC/pool bottleneck.

## Prioritized follow-up work

1. **Reduce repeated authentication/authorization/database work per request.** `requireEntryAccess()` calls `requireUser()` and then `requireSiteAccess()`, which authenticates again. Membership helpers can authenticate/query membership repeatedly. Carry a request-scoped principal, site and membership context through these helpers while preserving handler authorization, role checks, MFA and mutation protections. Start in [content/access.ts](../../src/server/content/access.ts:19) and [session.server.ts](../../src/lib/session.server.ts:85). Add query-count instrumentation and compare before/after with the same workload.
2. **Make list/count responses lean.** The sidebar issues one `listEntriesFn(limit:1)` per collection solely for counts, while `listEntries()` selects complete entry rows including content documents. Add a batched count endpoint and summary projections for collection lists. Inspect [sidebar.tsx](../../src/components/shell/sidebar.tsx:61), [entries.ts](../../src/server/content/entries.ts:111), and [fn/content.ts](../../src/server/fn/content.ts:167). Keep full documents behind editor reads. Measure RPC payload size, allocations, SQL count and tail latency after the change.
3. **Expose pool and event-loop metrics, then test pool/process tuning.** Record pool total/idle/waiting, acquisition wait, event-loop utilization/delay, and per-operation DB/S3 timings. The pool is currently created with the driver's default maximum in [db/index.ts](../../src/db/index.ts:21). Make any pool-size change a controlled A/B test; more connections can increase application CPU/GC pressure. Also evaluate two CMS workers/replicas, accounting for their shared CPU budget with PostgreSQL and RustFS. These are experiments, not demonstrated fixes.
4. **Reuse the S3 client/adapter and test internal routing.** [adapters/index.ts](../../src/adapters/index.ts:4) constructs a new adapter/client for each call; [storage/s3.ts](../../src/adapters/storage/s3.ts:29) constructs the client. Cache it for the immutable deployment configuration and use the shared Docker-network service address for server-to-server traffic. The public RustFS/console address can remain separate. Verify media preflight and repeat the storage check and full mixed benchmark.
5. **Retest the boundary after improvements.** Repeat 200 and 500, then use 250/300/400 if a tighter ceiling is needed. Only proceed to 1,000+ after the lower failing level passes. Keep the same fixtures, think times, role mix, response checks and resource guards.

## Scope and reproducibility

- VPS: 2 vCPUs, Intel Haswell-class virtual CPUs, 3.73 GiB RAM, no swap. CMS, PostgreSQL 18, Redis 8, RustFS and Traefik shared it. App image: `ghcr.io/seirai-dev/areca-cms:sha-c99900349d172cf8d2a0487283b1808e02e239fc`.
- Generator: a separate machine, 20 logical CPUs, about 48 GiB RAM; k6 2.3.0. Its CPU/memory were not exhausted. HTTP timing breakdowns and observed network traffic do not suggest it caused the multi-second server-wait cliff.
- Fixtures: 2,000 unique accounts/sessions; 40 clients, 80 sites, 240 collections, 13,200 initial entries, 1,800 JPEG assets. Groups share clients/sites; writable drafts are user-specific.
- Users made randomized state-dependent choices with think/edit times, including HTML arrivals/reloads, navigation, search/filter/paging, drafts/autosaves, publication/scheduling/archive/delete, media upload/download/selection and bounded client/site creation.
- Already-authenticated HTTP/SPA workflows were tested. Password-login/MFA throughput, browser rendering, external builds/deployments, AI and email flows were excluded. Admin MFA/session proofs were synthetic setup fixtures; normal request auth, authorization, CSRF and rate limits remained enabled.
- DB state was reset before each tier; old test blobs remained physically in RustFS, so disk consumption was cumulative and monitored. Monitoring/probe overhead was part of the observed VPS load.
- The database benchmark baseline was restored after diagnostics; the app recovered. No load-generator processes remain.
