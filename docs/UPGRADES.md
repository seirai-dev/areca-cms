# Upgrades, migrations and rollback

Database migrations are **forward-only**. There is no down migration, so the way
back from a bad upgrade is the pre-upgrade backup plus the previous image. Plan
every upgrade around that. Day-to-day monitoring is in
[OPERATIONS.md](OPERATIONS.md); backup and restore paths are summarized in
[RECOVERY.md](RECOVERY.md), with detailed Docker procedures in
[docker/RECOVERY.md](../docker/RECOVERY.md).

## Storage prefix upgrade note

The optional `S3_PREFIX` setting keeps database keys and public asset URLs
unchanged. Enabling or changing it requires a separate manual object move; see
[storage configuration](CONFIGURATION.md#storage-prefix).

Logical object keys are validated even when no prefix is configured. Empty
keys, empty path segments, `.`/`..` segments, backslashes and control characters
are rejected. All keys generated by Areca comply. Inspect unusual legacy
database keys and authoring bundles before upgrading; they may need a separate
repair. Malformed public asset keys return `404` without a storage request,
while invalid direct adapter operations still fail explicitly.

## How migrations run

### MCP grant binding update

The fixes from the [PR #6/#7 review](reviews/mcp-pr-6-7.md) bind OAuth tokens to
an individual approved connection generation. Previously issued OAuth tokens
must be replaced through a fresh consent flow after deploying these fixes.
Reconnect AI apps; personal MCP keys continue to work. Deploy the fixed version
to all replicas together, so an old replica cannot accept tokens that a fixed
replica rejects. These fixes reuse the existing OAuth tables and need no new
database migration.

Offline OAuth access no longer depends on an unexpired browser login session.
Its connection expires after ninety days without successful MCP use; refresh
alone does not extend that activity window. Scheduling now requires the
credential's “Allow going live” permission.

The image starts through `apps/cms/scripts/docker-entrypoint.mjs`, which on every
container start:

1. waits for PostgreSQL,
2. applies pending Drizzle migrations from `drizzle/` (recorded in
   `drizzle.__drizzle_migrations`),
3. creates the S3 bucket if it is missing,
4. starts the server (and, unless `WORKER_ENABLED=false`, the publish worker and
   scheduler in the same process).

Migrations therefore apply automatically the first time a new image starts. A
failed migration stops the container before the server starts. Do not assume the
database was left untouched; unless you have verified that nothing was applied,
treat a failed migration as requiring a restore (see Rollback).

Migrations are wrapped in a PostgreSQL advisory lock
(`scripts/lib/migration-lock.mjs`). If several containers start at once, one
migrates while the others wait (up to 10 minutes) and then find nothing to
apply. The lock protects the migration step only. It does not make rolling
upgrades safe: old and new code must not serve the same database at the same
time unless the release notes say the migration is backward compatible.

## Rules

- **One schema version at a time.** Stop every old replica and worker before
  starting the new image, then start a single new instance and wait until
  `/api/health` is healthy (migrations done) before scaling out. When scaling out
  is unavoidable, start extra replicas with `WORKER_ENABLED=false` so only one
  process runs the publish worker.
- **Back up first, every time.** Migrations can rewrite data (for example
  backfills). Take a coordinated backup as described in
  [RECOVERY.md](../docker/RECOVERY.md#coordinated-full-instance-backup) and keep it
  until the upgrade is accepted.
- **Pin the image.** Production must not follow `latest`. Set `CMS_IMAGE` to the
  commit tag (`ghcr.io/<owner>/areca-cms:sha-<full-commit-sha>`) or, for
  registry-enforced immutability, a digest (`...areca-cms@sha256:<digest>`).
  Record the tag/digest you ran before and after each upgrade; it is your
  rollback target. The third-party images in `docker/compose.yml` are pinned to
  explicit versions (PostgreSQL 17, Redis 8, RustFS, Mailpit); upgrade them as
  separate, deliberate changes. A PostgreSQL major version upgrade needs a
  dump/restore, not an image swap.
- **Keep secrets stable.** Do not change `DOKPLOY_CREDENTIALS_ENCRYPTION_KEY` or
  `BETTER_AUTH_SECRET` as part of an upgrade. Keep `AI_SETTINGS_ENCRYPTION_KEY`
  stable too if OpenRouter settings are configured. See _Secret handling_ in
  [DEPLOYMENT.md](DEPLOYMENT.md) and the full
  [configuration reference](CONFIGURATION.md).
- **Read the release's migration notes** (for example
  [HIGH_RISK_UPGRADE.md](HIGH_RISK_UPGRADE.md)). Some migrations freeze schedules
  or fail interrupted jobs and ask for manual review afterwards.

## Data corrections in migrations

- **`0012_was_live_correction` (rollback eligibility).** The old backfill in
  `0001_cheerful_tusk` marked every `superseded` release as having been live,
  including releases that were queued, coalesced and never built. After the
  upgrade, a release loses its "rollback" option only if there is no evidence
  it was ever deployed: no `deployed_at`, status other than `live`,
  `rolled_back` or `demo`, not a demo-mode release, and no succeeded build job.
  Live and demo rows are never touched. Releases with any evidence keep
  `was_live`, so a few historic false positives may remain, and a genuinely
  deployed release whose job history was pruned would lose rollback. Check the
  rollback list of important sites after upgrading; the data is not deleted
  and the correction can be repeated from a backup. It is safe to re-run.
- `0010`/`0011` are additive (`audit_log.organization_id` becomes nullable for
  instance-level events; `invitation` gains delivery-tracking columns).
- `0016_ai_settings_and_site_prompt` adds the singleton AI settings table and
  optional per-site SEO prompt. It does not rewrite existing content. AI key
  encryption uses `AI_SETTINGS_ENCRYPTION_KEY`; retain that key with backups if
  an encrypted provider key is configured.
- `0018_mcp_oauth` is additive. It adds the `mcp_connection` table and the OAuth
  authorization-server tables. Existing personal keys keep working. After you
  upgrade, set `APP_URL` and `BETTER_AUTH_URL` to the public HTTPS origin, and
  check that the reverse proxy forwards `/.well-known/*`, `/api/auth/*` and
  `/api/mcp/*` to the CMS. See [DEPLOYMENT.md](DEPLOYMENT.md#ai-apps-need-public-https).

## Procedure

1. **Choose the target.** Note the current image (tag or digest) and the target
   `sha-` tag. Confirm the commit's CI run (typecheck, unit tests, secret scans)
   passed.
2. **Back up production** with `node docker/recovery.mjs backup ...`. It stops
   the stack while capturing PostgreSQL, S3 and Redis, then you restart the
   original instance. Copy the archive off the host.
3. **Rehearse on a restored copy.** Restore the backup into a new, isolated
   project name with `node docker/recovery.mjs restore ...` (new volumes, other
   host ports, outbound deployments blocked, a different `APP_URL` as described
   in RECOVERY.md). Point `CMS_IMAGE` at the **target** image and start it. Check:
   - the container reaches healthy and the log shows `database migrations applied`,
   - sign in, open an unpublished draft, a revision and a live snapshot,
   - serve an uploaded asset,
   - row counts for organizations, sites, entries, revisions, publications and
     jobs match the source, and no job is stuck,
   - note how long migration took; this is your maintenance window.
     Discard the rehearsal project (`docker compose -p <name> down --volumes`)
     only after you have what you need.
4. **Announce a maintenance window** and stop the production stack (or at least
   every CMS container and worker). Confirm nothing else still writes to the
   database.
5. **Upgrade.** Update `CMS_IMAGE` to the target tag/digest, then
   `docker compose pull && docker compose up -d --wait`. The first container to
   start migrates; watch `docker compose logs -f cms`.
6. **Verify** with the same checks as the rehearsal. On an isolated site,
   explicitly select Demo mode to verify snapshot publishing, or configure a
   separate Dokploy application and health URL to verify Production deployment. Re-enable additional replicas and workers last.
7. **Keep** the backup and the previous image reference until the release has
   run through at least one normal publishing cycle.

## Rollback

Because migrations only go forward, rolling back means returning to the state
captured before the upgrade:

1. Stop every CMS container and worker.
2. Restore the pre-upgrade backup into **new** volumes
   (`node docker/recovery.mjs restore ...`), or into the original project after
   removing its volumes, using the **previous** image tag/digest recorded in the
   backup's pinned-image override.
3. Start it, verify as above, and cut over.
4. Anything written after the backup (edits, uploads, publications) is not in the
   restored copy. If that matters, export it first with the organization
   export in RECOVERY.md and reapply it afterwards, or decide not to roll back and
   fix forward.

Never point an older image at a database that a newer image has migrated.

If only the new _application_ misbehaves and the migration was purely additive,
the release notes may say fixing forward with a patched image is safe; otherwise
restore.

## Staging checklist

- [ ] Target `sha-` tag or digest chosen and its CI run is green.
- [ ] Release notes and migration notes read (`drizzle/` diff, upgrade docs).
- [ ] Fresh backup taken, copied off host, restore command tested before.
- [ ] Rehearsal on a restored copy with the target image: migration time noted,
      checks above passed, no stuck jobs.
- [ ] Maintenance window agreed; old replicas and workers stopped.
- [ ] Image pinned in the compose file / environment (no `latest`).
- [ ] Exactly one new instance started first; migrations logged as applied.
- [ ] Health, sign-in, draft, asset, and a demo publish verified.
- [ ] Extra replicas started with `WORKER_ENABLED=false`; one worker only.
- [ ] Previous image reference and backup retained for rollback.
