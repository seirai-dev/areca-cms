## How the CMS and SDK fit together

Editors save drafts; owners approve or freeze scheduled versions. Go live creates an immutable publication snapshot. A worker prepares the hosting build, the SDK pulls content into build-time files, Dokploy deploys the website, and a health response must identify the expected publication before production is marked live. Normal site pages consume built content; previews fetch draft data separately. Build tokens read content; schema tokens change the manifest. Client media is shared across its sites and remains publicly served by the CMS. MCP uses user-authorized site access and the same underlying content operations.

## Findings and decisions

“Code defect” means the behavior follows from the implementation, without necessarily exercising a live system. “Race traced” means a specific conflicting interleaving exists in code. “Conditional” means the problematic behavior requires the configuration or failure described. ### 01. Public signup can block first-run setup

**Priority/status:** High — Code defect.

**What is wrong:** An empty user table permits public signup without SETUP_TOKEN. An ordinary account then prevents setup from creating an admin; this is setup lockout, not automatic admin access.

**Possible fix:** Authorize the first account only through token-checked setup.

**Your decision:** Should the setup form and token be the only way to create the first account? Recommended: yes.

**Evidence:** `apps/cms/src/server/auth/registration-gate.ts:21`, `apps/cms/src/server/admin/setup.ts:47`.

### 02. An invited email can be registered by someone else

**Priority/status:** High — Code defect; attack chain traced.

**What is wrong:** Password signup checks for a pending invited email, not possession of its link or email ownership. A recipient later linking a verified social account and accepting the invite can activate the account while the attacker's password remains.

**Possible fix:** Require invitation possession or verified email ownership before account activation/linking.

**Your decision:** Require the invitation link, email verification, or both? Recommended: require the link at minimum.

**Evidence:** `apps/cms/src/server/auth/registration-gate.ts:35`, `apps/cms/src/lib/auth.ts:74`.

### 03. Failed setup can strand the instance

**Priority/status:** High — Code defect.

**What is wrong:** Better Auth creates the user/account outside the Drizzle transaction used for admin promotion and audit. A later failure leaves a non-admin user, blocking setup retries.

**Possible fix:** Make all bootstrap writes atomic or implement safe recovery.

**Your decision:** Should failed setup leave no account and allow retry with the same token? Recommended: yes.

**Evidence:** `apps/cms/src/server/admin/setup.ts:58`.

### 04. Revoking an invite can lose a race to acceptance

**Priority/status:** Medium — Race traced.

**What is wrong:** Acceptance reads the invite before its transaction, then grants membership without rechecking its token, expiry, or revocation. An old link can grant access after revoke/resend.

**Possible fix:** Lock and revalidate the invitation inside the acceptance transaction.

**Your decision:** Should whichever operation commits first determine access? Recommended: yes.

**Evidence:** `apps/cms/src/server/admin/members.ts:475`.

### 05. Repeated invitation acceptance can report failure
